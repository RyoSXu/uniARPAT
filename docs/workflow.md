# 协作流程

本页规定人员和 agent 如何在此仓库工作，是会话卫生的唯一事实来源；整体计划写在
`status.md`，固化结论写在 `decisions.md`。

## 开始任务

1. 阅读 `status.md`，再阅读 `index.md`；涉及指标或实验术语时继续阅读 `glossary.md`。
2. 检查 `git status --short`。保留无关工作，绝不覆盖。
3. 启动下一项实验前，确认上一项已有记录结论。一次只能认领 `status.md` 中的一项当前工作。
4. 涉及设计或数据改动时，修改代码或启动训练前先阅读关联设计和数据约定。

## 执行任务时

- 每次训练只保留一个实验因素。先做 10 epoch 的 pilot；只有记录结论后才能提升胜出方案。
- 每次训练使用唯一的 `--tag`。结果写入 `results/`；检查点和临时日志写入 `output/`，它们不是
  正式记录来源。
- 可复用的评估和结论判定脚本放在 `tools/eval/`，不得放入 `/tmp`。数据获取内容保留在 Git 外，
  不得悄悄重跑已冻结流程。
- 并行工作时，每个 agent 只写自己的日志文件。修改共享页面（`status.md`、`decisions.md`）或
  同一源文件前必须协调。不得把共享文档当作草稿板。

## 结束任务

1. 基于 `logs/_template.md` 新增日志：改动内容、证据、结论和下一项关卡工作。
2. 在 `status.md` 更新当前状态和下一项可执行工作。
3. 若工作改变后续安排，则更新 `status.md`；只有结论已确定且可复用时才更新 `decisions.md`。
4. 执行最小且相关的验证。代码改动需要相关测试；结构改动需要引用检查。

## 记录与保留

| 记录 | 存放位置 | 保留规则 |
|---|---|---|
| 当前状态、计划与阻塞项 | `docs/status.md` | 唯一整体计划；状态变化时改写，不累积细节历史。 |
| 已确定决策与基准事实 | `docs/decisions.md` | 简洁、有证据；只在结论确定后添加。 |
| 单个任务的证据 | `docs/logs/` 与 `results/` | 每个完成任务一份日志；结果 CSV 是正式记录。 |
| 拟议改动的设计 | `docs/design/` | 实施前写成。 |
| 已替代材料 | Git 历史 | 可恢复的背景，绝不作为运行指令。 |

## 命名规则

- 新文档使用小写 kebab-case：带日期记录用 `YYYY-MM-DD-主题.md`，长期说明用 `主题.md`。
- 工作日志使用 `log-YYYY-MM-DD-主题.md`。
- 实验标签使用简短、描述性的后缀，例如 `_e9ctl` 或 `_c5pilot`；不得将同一标签用于不同配置。
- 指标格式为 `e med/fail + p med/fail + (test|valid, epN, oracle|blind, Q1|pre-Q)`。
- 说明性文字一律使用中文；命令、路径、代码标识、项目代号和通用技术术语可保留英文。
